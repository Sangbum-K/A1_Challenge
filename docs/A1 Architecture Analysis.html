1. 대회가 뭔가요?

A1 CHALLENGE 는 자율주행 모델을 시뮬레이터(가상 세계)에서 실시간으로 운전 시켜 평가하는 대회다.

쉽게 말하면 — 컴퓨터 안에 가상 도시를 만들어 두고, 그 안에 가상 차량을 띄운 다음, 우리가 만든 AI가 그 차량을 운전하게 한다. 한 바퀴를 주행하는 동안 부딪히지 않고 차선을 잘 유지하며 속도를 적절히 내는지 채점한다.

항목 내용
시뮬레이터 MORAI — 한국에서 만든 자율주행 시뮬레이터. 가상 차량/카메라/도로를 제공
트랙 상암(도심)과 speedway(직선 위주) 두 종. 각각 난이도 mild/high
평가 한 바퀴 주행 — 추돌 회피 / 차선 유지 / 속도 적절성 / 컴퓨터 자원 사용량
제출물 학습된 모델 파일(.pt) 1개 + 운영 코드. 한 PC에서 4대 동시 주행

대회 규정 — 아키텍처를 제약하는 두 가지

대회에는 모델 구조에 직접 영향을 주는 규정 두 개가 있다:

  • §1.1: 모델은 파일 1개(.pt)여야 한다. 여러 파일로 쪼개면 안 됨
  • §1.3: 모델은 하나의 연결된 신경망 이어야 한다. "if 문으로 분기"나 "파이썬 코드로 후처리" 같은 건 안 됨. 입력→출력이 하나의 흐름 안에서 끝나야 함

이 규정이 나중에 "5개 모듈을 하나로 묶어야 한다"는 강제력으로 작용한다. 뒤에서 다시 나온다.

2. AI는 어떻게 "운전"을 배우나요?

핵심 개념: 모방 학습 (Imitation Learning)

이 팀이 쓴 방식은 모방 학습 이다. 쉽게 말하면:

운전을 잘하는 "선생"의 운전 기록을 보고, AI가 똑같이 따라 하는 것.

사람이 운전을 배울 때 — 시행착오로 직접 부딪혀 보며 배우는 것도 있지만 순서대로 가르쳐주는 사람 옆에서 "이 상황에서는 이렇게 핸들을 돌리고 이렇게 브레이크를 밟는구나"를 보고 따라 하는 게 빠르다. AI도 마찬가지다.

구체적으로는 이런 과정이다:

  1. 정답(정답 데이터) 을 만든다 — "이 상황에서는 핸들을 이 각도로 돌리고, 페달을 이 정도 밟아야 한다"는 기록
  2. AI에게 상황(입력) 을 보여주고, 정답(출력) 을 맞추게 한다
  3. AI가 정답과 다르게 내면, 그 차이만큼 스스로 수정 한다 (이게 "학습")
  4. 이걸 수만 번 반복하면, AI가 정답과 비슷한 행동을 하게 된다

정답은 누가 만드나요?

여기서 중요한 점 — 이 팀은 사람이 운전한 기록을 쓰지 않았다. 대신 규칙으로 짠 프로그램 이 운전한 기록을 정답으로 썼다.

"앞차가 5m 이내로 가까워지면 브레이크를 밟아라" 같은 규칙(rule)을 코딩해두고,
그 프로그램이 시뮬레이터에서 운전하는 것을 녹화해서 정답으로 삼는다.

왜 이렇게 하냐면 — 규칙으로 만든 정답이 더 일관되고, "이 상황에서 정확히 얼마나 브레이크를 밟아야 하는지"를 수학적으로 계산할 수 있기 때문이다. 이걸 GT(Ground Truth, 정답) 합성 이라고 부른다. 뒤에서 자세히 설명한다.

"학습"이라는 건 구체적으로 뭘 하는 건가요?

AI 모델은 수백만 개의 숫자(가중치, weight) 로 이루어져 있다. 학습이란 이 숫자들을 조금씩 수정해서, 입력을 넣었을 때 정답에 가까운 출력이 나오게 만드는 과정이다.

  • 입력을 넣는다 → AI가 뭔가 출력한다 → 정답과 비교한다 → 차이가 크면 숫자들을 수정한다
  • 이 한 사이클을 1 step 이라 하고 데이터 전체를 한 번 다 보면 1 epoch 이라 한다
  • 보통 수십~수백 epoch을 반복한다

이때 "숫자들을 수정"하는 것을 역전파(backward propagation) 라고 한다 — 출력의 오차가 입력 방향으로 거슬러 올라가면서 각 숫자가 오차에 얼마나 기여했는지 계산하고 기여가 큰 숫자를 더 많이 수정한다. "한 번의 순방향 계산(forward) → 한 번의 역방향 수정(backward)"이 하나의 연결된 흐름이어야 한다는 게 대회 규정 §1.3의 의미다.

3. 모델이 받는 것, 내는 것

AI는 0.05초마다 (초당 20번, 20 Hz) 한 번씩 주변 상황을 살피고 운전 명령을 내린다.

모델이 받는 것 (입력, 20 Hz)           모델이 내는 것 (출력, 20 Hz)
──────────────────────────           ──────────────────────────
camera   전방 카메라 이미지             steer    핸들 각도 (deg)
ego      내 차의 속도, 회전 속도         pedal    가속/제동 ([-1, +1])
traj     앞으로 갈 경로 30칸

입력 하나하나의 의미

camera (카메라) — 전방 카메라 한 대에서 온 이미지. 1280×720 픽셀인데, 그중 운전에 필요한 중간 띠(horizon strip) 만 잘라서 쓴다. 위쪽은 하늘이고 아래쪽은 차 앞후드/계기판이라 의미가 없기 때문. 결과적으로 250×1280 크기만 사용 — 계산량을 크게 줄여준다.

비유: 운전할 때 허공이나 내 계기판을 보지 않고 앞 도로만 보듯이 AI도 "보면 도움되는 영역"만 잘라서 본다.

ego (내 차 정보) — 내 차이 지금 얼마나 빠르게 달리고 있는지(vx, 속도), 얼마나 빠르게 회전하고 있는지(wz, yaw rate). 이 두 숫자만 쓴다.

traj (경로) — "이 길로 가라"라는 미리 정해진 경로. raceline(최적 주행선)이라는 CSV 파일에서, 앞으로 3초 동안 30개 지점의 (x좌표, y좌표, 권장 속도)를 가져온다.

주의할 점: 경로(traj)는 모델이 "만드는" 게 아니라 "받는" 것 이다. 모델이 "어디로 갈지"를 결정하는 게 아니라, 이미 정해진 길을 따라가면서 "얼마나 핸들을 돌리고, 얼마나 속도를 낼지"만 결정한다. 내비게이션이 길을 알려주면 운전자는 그 길을 따라 가듯이.

출력의 의미

steer (조향) — 핸들 각도. 양수=좌회전, 음수=우회전

pedal (페달) — +는 가속(throttle), −는 제동(brake). 이 값을 차량의 물리 모델에 넣으면 실제 가속도(m/s²)로 변환된다.

왜 카메라를 1대만 쓰나요?

대회 시뮬레이터는 5대 카메라(전방, 좌후, 우후, 좌측, 우측)를 다 제공한다. 하지만 다 쓰면 모델이 무거워지고 느려진다. 이 팀에게 필요한 건 "앞차가 있는지, 얼마나 떨어져 있는지, 다가오는지" — 그래서 전방 1대만 쓴다. 한 PC에서 4대를 동시에 돌려야 하는 본선 환경에서 GPU가 버티려면 이런 선택이 필수다.

4. SCC — 앞차 안 부딪히게 하기

SCC가 뭔가요?

SCC(Smart Cruise Control, 스마트 크루즈 컨트롤) 는 앞차(lead vehicle)와의 거리와 상대속도를 보고 자동으로 가속/제동을 조절하는 기능이다.

앞차가 가까워지면 브레이크를 밟고, 없거나 멀면 그냥 정해진 속도로 달린다.

요즘 자동차에 있는 "어댑티브 크루즈 컨트롤"과 같은 기능이다. 고속도로에서 앞차와 거리를 유지하면서 알아서 속도를 조절하는 그것.

왜 이게 대회의 핵심인가요?

이 팀에게는 이미 잘 달리는 모델 이 있었다 (뒤에서 자세히 설명). 정해진 경로를 따라 부드럽게 달리는 건 잘했다. 문제는 — 앞에 차가 있어도 못 보고 그냥 들이받는다 는 것. 대회 평가에서 추돌 회피는 필수 항목이다. 그래서 "이 잘 달리는 모델에 SCC만 추가하자"가 이 프로젝트의 출발점이 됐다.

SCC에 필요한 정보들

SCC가 제대로 작동하려면 모델이 앞차의 이런 정보를 알아야 한다:

정보 설명 비유
lead presence 앞차가 내 차선에 있는지 없는지 "앞에 차 있어?"
거리 앞차와의 거리 (m) "얼마나 떨어져 있어?"
vL_rel (상대속도) 앞차 속도 - 내 차 속도. 음수면 가까워지고 있음(closing), 양수면 멀어지고 있음 "앞차가 다가오고 있어? 멀어지고 있어?"
TTC (충돌까지 시간) 거리 / 상대속도. 작을수록 위급 "지금 속도면 몇 초 뒤에 부딪혀?"

이 정보들을 카메라 이미지에서 뽑아내는 게 이 프로젝트의 핵심 기술 중 하나다.

5. 진짜 시험은 closed loop다

open loop vs closed loop

AI 모델을 평가하는 데는 두 가지 방식이 있다:

open loop — 학습/검증할 때 쓰는 방식

한 장면(입력)을 보여주고, AI가 뭐라고 답하는지(출력)를 정답과 비교한다.
마치 시험지를 풀고 채점하는 것. 빠르고 간단하다.

closed loop — 실제 평가할 때 쓰는 방식

시뮬레이터에 AI를 띄우고, 실시간으로 0.05초마다 운전 명령을 내린다.
AI가 이번에 내린 명령이 다음 장면에 영향을 준다 — 핸들을 돌리면 차가 돌아가고, 그러면 카메라에 보이는 화면이 바뀐다.

왜 closed loop가 무서운가요?

closed loop에서는 한 번의 실수가 연쇄적으로 퍼진다 (cascading):

  • AI가 0.05초 동안 이상한 페달 값을 내뱉음
  • → 차가 갑자기 급정거함
  • → 다음 화면이 이상해짐 (차가 멈춰 있으니까)
  • → AI가 또 이상한 값을 내뱉음
  • → 계속 무너짐

비유: 시험지를 풀 때는 한 문제를 틀려도 다음 문제는 안 바뀐다 (open loop). 하지만 실제 운전에서는 핸들을 잘못 돌리면 차가 도로를 벗어나고, 그러면 다음 순간의 상황이 완전히 달라진다 (closed loop).

대회 채점은 closed loop로 한다. 그래서 학습 점수(open loop)가 아무리 좋아도 closed loop에서 한 번 삐끗하면 의미가 없다. 이 팀이 9일 동안 겪은 많은 사고가 바로 "학습은 잘 됐는데 실제 운전시키니까 이상하다"는 패턴이었다.

6. 이름 규칙 — f, a, i 가 뭔가요?

뒤에 나올 아키텍처에서 f_1, f_2, a_2, a_2_aux, i_1, i_2 같은 이름이 계속 나온다. 겁먹을 필요 없다 — 이건 팀이 모듈과 데이터에 붙인 별명 이다. 한 번 정리하고 가면 뒤가 훨씬 편하다.

세 가지 알파벳의 의미

팀은 모듈과 데이터를 세 가지 알파벳 으로 나누었다:

알파벳 의미 비유
f function — 최종 출력을 만드는 메인 모듈 "요리사" — 재료를 받아 완성된 요리를 내놓는 사람
a attention/auxiliary — 중간 처리를 담당하는 모듈 "조리 보조" — 재료를 손질하고 합치는 사람
i intermediate — 모듈 사이를 흐르는 중간 데이터 "준비된 재료" — 조리 보조가 손질해서 요리사에게 건네는 것

f — 최종 출력을 만드는 모듈

이름 역할 비유
f_1 (main) 경로 + 내 차 정보만 보고, 핸들 각도와 기본 페달 을 결정 "메인 요리사" — 레시피(경로)를 보고 기본 요리를 만드는 사람. 이 사람은 눈으로 재료를 보지 않고, 레시피 글만 읽고 요리한다 (text-only). 이미 검증된 실력자라 가르치지 않는다 (frozen)
f_2 (side) 카메라 정보를 보고, 앞차가 가까우면 브레이크 보정치(delta) 만 계산 "보조 요리사" — 메인이 만든 요리에, 눈으로 재료 상태를 보면서 "조금 덜 익혀야겠다" 하고 마지막 보정만 한다

핵심: f_1이 "기본 운전"을 하고, f_2가 "앞차 안 부딪히게 브레이크 보정"만 추가한다.
f_1은 건드리지 않고(frozen), f_2만 학습시킨다.

a — 중간 처리를 담당하는 모듈

  • 모듈(f, a)은 학습/얼리기(freeze)/저장(ckpt)의 단위다 — "이 모듈의 숫자들을 수정할까, 말까?"를 결정한다
  • 피쳐(i)는 저장(cache)의 단위다 — "이 중간 데이터를 미리 만들어둘까, 매번 새로 만들까?"를 결정한다

이 구분이 중요한 이유는, 9일 중 가장 뼈아픈 사고들이 "모듈의 숫자는 같은데, 모듈 사이를 흐르는 데이터(i_2)가 학습할 때와 실제 운전할 때 다르게 만들어지는" 문제였기 때문이다. 같은 모듈인데 데이터가 다르니, 똑같은 사진을 넣어도 다른 결과가 나온다. 이걸 i2_mem mismatch 라고 부른다 — 뒤에서 다시 나온다.

핵심 개념: token, attention, transformer

지금까지 모듈 이름과 역할을 정리했다. 여기서부터는 다이어그램에 등장하는 token, self-attn, cross-attn, transformer 가 뭔지를 풀어 설명한다. 이 개념들을 알고 나면 뒤에 나오는 모든 아키텍처 다이어그램이 읽힌다.

token — 정보의 최소 단위

모델은 이미지나 경로를 통째로 한 번에 처리하지 않는다. 작은 조각으로 나눠서 처리한다. 이 조각 하나하나를 token 이라고 부른다. 각 토큰은 여러 숫자로 이루어진 작은 배열(tensor, 텐서)이다 — 이미지의 한 조각이면 그 조각의 색상/질감 정보가 담긴 숫자들이고, 경로의 한 지점이면 (x, y, 속도) 세 숫자가 담긴다.

비유: 요리사가 재료를 통째로 다루지 않고 먼저 잘게 썰어서 준비해두듯이, 모델도 데이터를 토큰 단위로 쪼개서 다룬다.

이 모델에서 나오는 토큰들:

토큰 개수 내용
i_1 토큰 40개 이미지를 가로 방향으로 40등분한 요약. 각 토큰이 이미지의 한 조각을 담당
traj 토큰 30개 경로의 30 step. 각 토큰이 "0.1초 뒤에 (x, y) 위치에서 v 속도로 가라"는 정보
ego 토큰 1개 내 차 속도(vx)와 회전 속도(wz). 이걸 traj의 첫 번째 토큰에 끼워넣는다(prepend)

ego를 첫 토큰에 끼워넣는 이유

5/19 설계 합의의 핵심 결정 중 하나. 원래는 ego 정보를 모든 처리가 끝난 뒤에 더하려 했다. 그런데 그러면 ego가 다른 토큰들과 "대화"할 기회가 없다.

ego를 traj의 첫 번째 토큰에 끼워넣고 나서 self-attention을 돌리면, "내가 지금 어떤 자세인지"가 30개 토큰 전체로 퍼진다. 속도가 빠르면 경로의 모든 지점이 그 속도를 감안하고, 회전 중이면 모든 지점이 그 회전을 감안한다.

비유: 요리사가 "오늘 불이 세다"는 정보를 맨 마지막에 알려주는 것보다, 처음부터 알려주면 모든 요리 과정에서 불 세기를 감안하게 되는 것과 같다.

self-attention — 같은 그룹 안에서 정보 교환

self-attention 은 같은 출처의 토큰들끼리 서로 정보를 주고받는 메커니즘이다. 모든 토큰이 다른 모든 토큰을 "살펴보고" 자기에게 필요한 정보를 끌어온다.

비유: 요리사가 모든 재료를 탁자에 펼쳐놓고, 각 재료가 다른 재료와 어떤 관계인지 살펴보면서 요리 계획을 세우는 것.

이 모델에서 self-attention이 쓰이는 곳:

  • a_2 — 현재 이미지의 40 토큰 + 이전 이미지의 40 토큰을 같이 놓고 self-attention → 두 시점을 비교해서 "뭐가 움직였는지" 파악. 이게 "이미지 합치기(fusion)"의 실제 방식이다
  • f_1 (controller_imitator) — traj 30 토큰 + ego(첫 토큰에 끼워넣음)를 self-attention → 경로의 각 지점이 다른 지점과 내 차 상태를 감안해서 핸들/페달 결정

cross-attention — 다른 그룹에서 정보 가져오기

cross-attention 은 한 그룹의 토큰이 다른 그룹의 토큰에서 필요한 정보를 끌어오는 메커니즘이다. "질문(query)" 쪽과 "답(key/value)" 쪽이 따로 있다.

비유: 요리사가 레시피(질문)를 보면서, 동시에 재료 사진(답)을 확인해서 "이 요리 단계에서 재료 상태가 어떤가?"를 사진에서 찾아오는 것.

이 모델에서 cross-attention이 쓰이는 곳:

  • f_2 (side) — 경로 정보(질문)에 이미지 기억 i_2(답)를 대조. "이 경로 위치에서 앞차가 가까운가?"를 이미지에서 찾아옴. 다이어그램에 cross-attn(i_2) 라고 표시된 부분이 바로 이것이다

transformer — attention을 층으로 쌓은 구조

transformer 는 self-attention과 cross-attention을 여러 층(layer)으로 쌓아서 만든 모델 구조다. 한 층에서 정보 교환을 하고, 그 결과를 다음 층으로 넘기고, 또 정보 교환을 하고...를 반복해서 점점 더 정교한 이해를 만든다.

비유: 여러 명의 요리사가 줄줄이 서서, 첫 번째가 재료를 대충 분류하고, 두 번째가 더 세밀하게 나누고, 세 번째가 최종 판단을 하는 것. 층이 깊을수록 더 정교한 이해가 된다.

이 프로젝트에서 transformer가 나오는 곳:

모델 구조 설명
controller_imitator (f_1 원본) text-only transformer 경로 + ego 토큰만 받아서 self-attention 층들을 통과시켜 핸들 + 페달 출력. 카메라를 안 봄
첫 시도 모델 (v6~v18, 실패) concat + SelfAttn 이미지 + 경로 + ego를 한 번에 이어 붙이고(concat) self-attention → 이미지 노이즈가 경로 처리를 흔듦
5/24 이후 f_1 frozen + f_2 cross-attn f_1은 text-only transformer 그대로(frozen), f_2는 cross-attn으로 이미지 정보만 가져옴

Δyaw token shift — 이전 이미지를 현재 기준으로 맞추기

a_2가 현재 + 이전 이미지를 합칠 때, 이전 이미지는 내 차가 회전한 만큼(Δyaw) 가로로 밀어서 현재 기준으로 맞춘다. 이렇게 하면 encoder를 다시 돌릴 필요 없이, 저장된 i_1 토큰을 가로로 shift만 하면 된다 — 이게 i_1 cache가 가능한 핵심 이유다.

비유: 어제 찍은 사진과 오늘 사진을 비교하려면, 어제 사진을 내가 선 자리로 살짝 돌려서 맞춰놓고 비교하는 것. 매번 새로 찍을 필요 없이 저장된 사진을 살짝 돌리기만 하면 된다.

쉽게 풀어서 설명

  1. 원본 데이터 — 시뮬레이터나 실제 차량이 주행하면서 녹화한 데이터. 매 순간의 "내 차 위치, 주변 차량 위치, 차선 정보"가 들어있다.

  2. SCC 재계획 (scc_replanner) — 원본 경로를 보고 앞차가 내 차선에 있으면 속도를 재조정한다. 여기서 Frenet 좌표 라는 게 나오는데 어려운 게 아니다 — 경로를 따라간 거리(s)와 경로에서 옆으로 떨어진 거리(n)로 위치를 표현하는 방식이다. "앞차가 내 차선 안에 있나?"가 |n| ≤ 차선 절반 폭 한 줄로 판정된다.

  3. MPC 최적화 — 재조정된 경로를 물리적으로 실현 가능한 가속도/브레이크 명령으로 바꾼다. MPC(Model Predictive Control)는 "앞으로 몇 초 동안 어떻게 운전하면 가장 부드럽게 목표를 달성할까"를 수학적으로 푸는 기법이다.

중요한 설계 결정들

  • 기존 코드를 버리고 새로 짰다 (5/19) — 이전에 쓰던 acados 기반 MPC를 버리고, HPIPM 기반 LMPC로 처음부터 다시 짰다. "기존 코드 재활용"의 유혹은 거의 항상 비싸다
  • 제약(constraint)을 느슨하게 — 정답을 만들 때의 가속도/급가속 한계를 실제 운전 때의 한계보다 느슨하게 잡았다. 빡빡하게 잡으면 급정거해야 하는 상황에서 "수학적으로 풀 수 있는 답"이 없어지고, 그러면 그 상황의 정답이 빠진다. 정답이 빠지면 AI가 그 상황을 못 배운다
  • 매번 초기화 — 최적화 도구가 한 번 실패하면 그 상태를 다음 번에도 들고 가서 연쇄 실패가 난다. 매번 초기화하고 5번 예비 계산을 돌려서 이걸 막았다. 실패율이 한 자리 수 %에서 거의 0%로 떨어졌다

각 단계 설명

1단계 — 이미지 이해: EfficientNetV2(Google이 만든 이미지 인식 모델)에 SAM(Segment Anything Model)의 분할 결과를 가르쳐서, 사진을 보면 "여기가 차선, 저기가 차"를 알게 한다. 1단계가 끝나면 backbone(이미지를 이해하는 부분)의 숫자들은 고정한다(frozen).

1단계 학습 결과 샘플. seg backbone이 학습한 차량(적색 계열)과 차선(청색 계열) segmentation을 여러 장면에 overlay한 모습. 이 결과가 i_1(이미지 요약)의 기반 — 2단계에서 이 요약을 바탕으로 앞차를 찾는다.

2단계 — 이미지 합치기 + 앞차 인지: 1단계에서 만든 이미지 요약(i_1) 두 개(현재+이전)를 a_2가 합쳐서 i_2를 만든다. 그 위에 a_2_aux가 얹혀서 "앞차가 있나, 거리가 얼마나, 다가오나"를 7개 숫자로 뽑아낸다.

3단계 — 운전 명령: f_1은 이미 학습된 모델(Professor #654)을 그대로 쓴다(frozen). f_2만 새로 학습한다 — i_2와 앞차 정보를 보고 브레이크 보정치(delta)를 계산하는 법을 배운다.

  • i_1 cache — 1단계 모델이 이미지를 처리한 결과(i_1)를 미리 저장해둔다. 그러면 2단계 학습할 때 매번 이미지를 다시 처리할 필요 없이, 저장된 i_1만 불러오면 된다. 학습 속도가 한 자리 수 분 단위로 줄어든다
  • prebake (사전 구움) — 학습 직전에 이미지, 라벨, 부가 정보를 하나의 파일로 통째로 묶어 “구워두는” 작업. 매 학습마다 이미지를 읽고 처리하는 시간을 아끼기 위해서다. 마치 요리사가 미리 재료를 손질해서 냉장고에 넣어두고, 요리할 때 꺼내 쓰는 것과 같다
  • warm-start (웜스타트) — 이전에 학습한 가장 좋은 모델( best checkpoint)에서 이어서 학습하는 것. 처음부터 새로 학습하는 것보다 안정적이고 빠르다. 마치 요리사가 레시피를 처음부터 개발하는 게 아니라, 이미 검증된 레시피에서 시작해서 살짝 수정하는 것과 같다
  • Professor #654 — 5월 15일경 이미 학습된 text-only 모델. 경로만 보고 핸들+페달을 결정하는 데 val L1(평균 오차) 0.0355라는 매우 좋은 성능. 이걸 f_1의 초기값으로 쓰면 처음부터 강한 출발점

★ v7 — "학습은 잘 됐는데 실제로 안 된다"의 전형

v3~v6까지 "앞차 속도(vL_rel) 추정이 영원히 안 됨" — 앞차가 다가오는데도 속도 추정값이 0으로 고정.

원인 — 손실 함수(loss)에 두 가지가 누락:

  1. 정규화(normalize) 누락 — 앞차 속도의 단위가 다른 정보들과 안 맞아서, 다른 정보의 학습에 묻혀버림
  2. 마스크 누락 — 앞차가 없는 프레임도 "앞차 속도 = 0"이라고 학습해서, 평균이 0으로 깎임 → 추정값이 항상 0에 수렴

비유: 시험에서 "문제가 없는 빈칸도 0점 처리"하면, 학생이 "어떤 문제든 0이라고 찍는 게" 평균 점수가 높다고 착각한다.

왜 발견이 늦었나 — 손실 곡선(loss curve)은 잘 떨어지는 것처럼 보였다. 대부분의 프레임이 앞차 없음(정답=0)이라서, 0으로 찍기만 해도 점수가 괜찮아 보였기 때문. 발견은 "추정값의 분산이 0인가?" 한 번 찍어보고 나서야 했다.

Fix (v7):

# v5/v6 (버그)
loss = L1_loss(추정값, 정답)                    # 정규화 없음, 앞차 없는 프레임도 포함

# v7 (수정)
loss = L1_loss(
    (추정값 - 평균) / 표준편차,                   # 정규화
    (정답  - 평규) / 표준편차,
)
loss = (loss * 앞차있음_마스크).평균()            # 앞차 있는 프레임만 학습

v4 — focal loss로 거짓 경보 줄이기

데이터의 대부분은 "앞차 없음"이다. 일반적인 손실 함수인 BCE(Binary Cross-Entropy, 이진 교차 엔트로피 — "예/아니오" 둘 중 하나를 맞추는 확률 문제에서 쓰는 기본 손실 함수)를 쓰면 AI가 "일단 앞차 있다고 해놓는 게" 평균 점수가 높다고 착각한다. focal loss는 "이미 잘 맞춘 쉬운 문제(앞차 없음)"의 점수 비중을 낮추고 "어려운 문제(앞차 있음, 특히 가까운 경우)"에 집중하게 만든다.

v3 와 v4 의 성능 비교 막대 그래프. Accuracy, Precision, Recall, F1, Specificity 5개 지표를 비교한다. focal loss 를 도입한 v4 가 전 지표에서 크게 올라갔다 — 특히 Precision(정밀도 — "앞차 있다고 한 것 중 실제로 앞차인 비율")과 Recall(재현율 — "실제 앞차 중 모델이 잡아낸 비율")이 모두 70점대에서 97점대로 급등했다. 즉 거짓 경보(FP)도 줄이면서 진짜 앞차 검출 능력도 함께 향상된 것이다.

v4 학습 곡선. epoch별 train / val L1(오차, 낮을수록 좋음)과 lead presence(앞차 유무 판정) Precision / Recall을 보여준다. 빨간 점선은 v3의 같은 epoch 비교이다. v4의 P/R 모두 v3보다 위 — 특히 Precision(정밀도 — "앞차 있다고 한 것 중 실제로 앞차인 비율")이 의미 있게 높다. 거짓 경보가 줄었다는 뜻이다.
