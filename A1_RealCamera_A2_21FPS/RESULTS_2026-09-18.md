# 2026-09-18 실외 카트 인식 시험 기록

Hikrobot 실물 카메라 → `camera_aravis2/ROS2` → seg-pretrained EfficientNetV2-S → i₁ →
21-frame `A2ModelMultiFrame` → a₂ 경로를 **실외에서 실제 차량 대상으로** 처음 돌린 기록이다.
2026-09-14 실내 모니터 재촬영의 후속이다.

## 한 줄 결론

21 FPS는 **실패**했고(16.45 FPS), 인식률도 낮았다(중앙 lead 7.67%). 다만 두 문제의 원인은
모델이 무거워서가 아니다. 같은 모델·같은 입력 geometry가 같은 날 실내에서는
**compute p95 14.4 ms**로 돌았고 실외 카트에서는 **49.5 ms**로 돌았다. 3.6배 느려진 원인은
**커널/부팅 설정**이다. 실내 run 1~3은 generic 커널, 실외 run 4·5는 A1-BSW realtime 부팅
항목에서 돌았다. 2026-09-22 실내 재측정으로 확정했다(11절). 인식률은 **노출**이 주원인이다.

> **2026-09-22 정정**: 최초 작성 시 이 문서는 커널을 "9-18 = generic, 9-14 기준선 = realtime"으로
> 기록했고, 저하 원인을 실외 전원/클럭 상태로 추정했다. 부팅 로그 대조 결과 **둘 다 반대**였다.
> 1절 환경표, 3절, 7절, 10절을 고쳤고 근거는 11절에 있다.

## 3. 결과 1 — 처리량: 21 FPS 실패

### 측정값 (run 4·5)

```
a₂ 출력        16.45 FPS          (목표 21, 예산 47.62 ms)
compute p50    49.5 ms
capture→a₂ p95 92.8 / 94.2 ms
카메라 수신    20.99 FPS          ← 카메라는 정상
버려진 frame   21.7 %             (run5: 76877 수신 중 16637 drop)
history unique 20개 중 p50 16개, frame의 83~93 %가 20개 미만
```

카메라 acquisition은 멀쩡했다. 병목은 전적으로 추론이다.

### 단계별 비교 — 모든 단계가 균일하게 느려졌다

| 단계 | 실내 run 1~3 (중앙값) | 실외 run 4~5 (중앙값) | 배수 |
|---|---|---|---|
| preprocess (CPU) | 3.8 ms | 8.3 ms | 2.2× |
| backbone (GPU) | 6.0 ms | 22.5 ms | 3.8× |
| a₂ (GPU) | 4.6 ms | 17.7 ms | 3.8× |
| **compute 합** | **13.7 ms** | **49.5 ms** | **3.6×** |

입력 geometry, 모델, checkpoint, 코드가 모두 동일한데 CPU와 GPU가 **함께** 느려졌다.

### 시간에 따른 열화가 아니다

10분할 구간별 중앙값을 보면 run 4·5 모두 **첫 프레임부터 이미 49 ms**다.
run 5는 오히려 36~54분 구간에서 30~34 ms로 빨라졌다가 다시 49 ms로 돌아왔다.

```
run5 구간별 compute 중앙값 (분)
 0.0  6.1 12.2 18.3 24.4 30.5 36.6 42.7 48.8 54.9
49.5 49.6 49.6 49.6 49.3 49.7 34.3 34.3 30.7 49.3
```

누적 발열이면 단조 증가해야 한다. 그렇지 않으므로 **발열 누적이 아니다.** 저하는 run 3과
run 4 사이의 재부팅, 즉 **generic → realtime 커널 전환 시점과 정확히 일치**한다.
처음에는 실내 → 실외(카트 전원) 이동 탓으로 봤지만, 같은 RT 설정을 실내 책상 전원에서
재현해 전원 가설을 기각했다(11절). 36~54분 구간의 30~34 ms는 스레드가 놓인 코어 종류
(P-core/E-core)나 `ondemand` 클럭 변동 때문으로 추정하며, 아직 검증하지 않았다.

### history 품질 붕괴 (2차 피해)

frame을 21.7 % 버리면 21-frame temporal 구조가 깨진다. 과거 20개 slot의 고유 source가
중앙값 16개로 떨어졌고, 같은 frame이 여러 시간 slot을 채운다. 이건 단순한 FPS 저하가
아니라 **a₂의 속도 채널(vL_rel) 입력 자체가 왜곡**된다는 뜻이다. 인식률 저하의 일부는
여기서 온다.

### 화면에서 확인된 것

실내 모니터용 노출값 20000~25000 µs를 그대로 실외에서 썼다. 결과:

- run 4 초반(실내 이동 중): `crushed 23.5 %` → **UNDEREXPOSED**
- run 4 후반(실외): `clipped 22.2 %` → **OVEREXPOSED**, 모델 band의 22 %가 백색 포화
- `BalanceWhiteAuto=Off` 때문에 강한 녹황색 캐스트

고정 노출 하나로 실내 이동과 실외 주간을 모두 덮을 수 없다. 화면 상단 경고
(`<< OVEREXPOSED`)는 정상 동작했다 — 표시는 됐지만 조치하지 않은 채 run이 진행됐다.

포화된 band에서는 backbone이 쓸 수 있는 텍스처가 사라지므로 검출률 저하는 당연한 결과다.
검출이 된 경우는 값 자체는 그럴듯했다(예: `b18 p=0.63 d=25.8 m vrel=+18.8 m/s`, 이탈 방향).

## 5. 산출물 일부 유실

run 5(61분, 본 시험)는 **`summary.json`이 없고 `a2_overlay.mp4`가 재생 불가**다.

- mp4 1.88 GB에 `ftyp`/`free`/`mdat`만 있고 **`moov` atom이 없다** → 인덱스 미기록
- 원인: 프로세스가 `q`/Ctrl-C가 아니라 SIGTERM/kill로 종료되어 `finally`의
  `video_writer.release()`와 `summary.json` 기록이 실행되지 않음
- `frames.jsonl`(637 MB)은 주기적으로 flush되므로 살아남았고, 위 분석은 전부 이걸로 했다

**조치 필요**: runner가 SIGTERM에서도 정상 종료하도록 핸들러 추가. 61분짜리 현장 데이터를
다시 잃지 않으려면 필요하다.

## 6. "처음부터 크롭해서 받아오자"에 대한 검토

결론부터: **hardware crop은 이 문제를 해결하지 못한다.**

지금도 backbone에 들어가는 입력은 이미 `(1, 3, 250, 1280)`이다. 소프트웨어 crop이
backbone **앞에서** 끝나기 때문이다(`[contract] image=(1,3,250,1280)`로 매 run 확인됨).

| 단계 | run 4·5 비용 | 센서 crop 시 |
|---|---|---|
| backbone | 22.5 ms | **변화 없음** (입력이 이미 250×1280) |
| a₂ | 17.7 ms | **변화 없음** (token 연산) |
| preprocess | 8.3 ms | 일부만 감소 |

즉 49.5 ms 중 **40.2 ms는 센서 crop과 무관하다**. 반면 실내에서는 같은 파이프라인이
13.7 ms로 돌았고 이는 47.62 ms 예산의 **3.5배 여유**다. 고쳐야 할 것은 geometry가 아니라
3.6배 느려진 RT 부팅 설정이다.

### 그래도 센서 crop이 가치 있는 부분

`cv_bridge` debayer는 ROS 콜백 스레드에서 **1280×720 전체**를 처리한다(`compute_ms`에
포함되지 않아 위 표에는 안 잡히지만 CPU는 쓴다). 센서에서 250행만 받으면:

- 전송량 921,600 → 320,000 B/frame (65 % 감소), 19.4 → 6.7 MB/s
- debayer 대상 65 % 감소

**geometry는 그대로 유지 가능하다.** 현재 모델이 보는 영역은 센서 행 475..725이므로:

```
Width=1280  Height=250  OffsetX=320  OffsetY=475
--roi-y0 0  --roi-y1 250
```

이러면 픽셀 단위로 지금과 동일한 영역이다. 단 화면에서 전체 frame 맥락(초록 박스 밖)이
사라져 조준이 어려워지는 trade-off가 있다. **처리량 문제를 먼저 해결한 뒤** 부가 최적화로
검토할 것을 권한다.

## 7. 다음에 할 일 (우선순위)

1. **커널/부팅 설정** — 원인 확정(11절). 가장 중요하다.
   - 가장 빠른 해결: 실외 run을 **generic 커널**로 부팅한다(실측 compute p95 14.4 ms).
   - RT 커널이 필요하면(제어팀과 PC 공유), 제어 코어 8–15는 건드리지 않고 다음을 시험한다.
     - 추론 프로세스를 P-core에 고정: `taskset -c 0-3`
     - 우리 코어의 governor를 `performance`로 설정
     - 제어팀과 협의해 `intel_pstate=disable` 대신, intel_pstate를 켠 채 제어 코어만
       min=max로 클럭을 고정 (터보가 살아나 2.1 GHz 상한이 풀린다)
   - PREEMPT_RT 커널 자체와 부팅 옵션의 영향은 아직 분리하지 않았다.

2. **노출** — 실외에서는 고정값을 실내값 그대로 쓰지 않는다.
   ```bash
   ./run.sh aim          # [ / ] 로 조절, clipped < 5 % 맞추기
   ```
   카트가 그늘과 양지를 오가면 auto가 낫다(실물에서 동작 확인됨).
   ```bash
   ./run.sh live --exposure auto --exposure-max 2000
   ```

3. **화이트밸런스** `Continuous` 적용 — 녹황색 캐스트 제거.

4. **SIGTERM 핸들러 추가** — run 5 같은 산출물 유실 방지.

5. 1~4 해결 후에도 여유가 필요하면 그때 **센서 hardware crop**(6절 설정) 적용.

6. 다음 실외 run은 `--bag`으로 원본을 남긴다. 현장 재현이 비싸고, `./run.sh replay`로
   노출·threshold를 바꿔가며 몇 번이든 다시 볼 수 있다.

## 10. 이번 시험으로 말할 수 있는 것

- 실물 카메라 acquisition은 실외에서도 21 FPS로 안정적이었다(20.99 FPS, 카메라 측 문제 없음).

  여유로 통과했으므로 모델 용량 문제로 결론 내릴 근거는 없다. 실패 원인은 RT 부팅
  설정이다(11절).

- 거리·상대속도의 **수치 정확도는 여전히 주장할 수 없다.** calibration 근거가 없고
  (`geometry_valid_for_accuracy=false`), 이번엔 노출 포화와 history 붕괴까지 겹쳤다.

- **장소·전원을 실내 책상으로 되돌려도 realtime이면 49.7 ms가 나온다.** generic이면 13.7 ms다.
  따라서 저하 요인은 장소나 카트 전원이 아니라 커널/부팅 설정이다.
- 모든 단계(CPU preprocess, GPU backbone, GPU a₂)가 같은 비율로 느려지는 양상도 세 조건에서
  일관된다. batch 1 추론은 GPU 커널 launch가 CPU 쪽에서 묶이므로, CPU가 느려지면 GPU
  단계도 함께 느려진다.

### 느린 부팅 설정의 내용

GRUB 항목 `A1-BSW 운용` (9-18 run 4·5와 9-22 재측정에 같은 cmdline으로 부팅됨):

```
6.8.1-1059-realtime (PREEMPT_RT)
isolcpus=managed_irq,domain,8-15 nohz_full=8-15 rcu_nocbs=8-15 rcu_nocb_poll
irqaffinity=0-7,16-19 intel_idle.max_cstate=0 processor.max_cstate=0
idle=poll intel_pstate=disable cpufreq.default_governor=performance
부팅 후 iso_pm.sh eco 800, housekeeping ondemand
```

9-22 측정 중 실측 CPU 상태 (i7-12700: P-core 0–15, E-core 16–19):

| 항목 | 값 |
|---|---|
| 주파수 드라이버 | `acpi-cpufreq` (intel_pstate 꺼짐) |
| P-core 최대 클럭 | 2.1 GHz. 터보(최대 4.9 GHz)를 못 쓴다 |
| 코어 0–7, 16–19 governor | `ondemand`. 측정 중 1.3~3.5 GHz로 변동 |
| 코어 8–15 | 제어용으로 격리, `performance`, 800 MHz 고정 |

### 아직 확정하지 않은 것

- PREEMPT_RT 커널 자체의 영향과 부팅 옵션(`intel_pstate=disable`, `isolcpus`, `iso_pm.sh`)의
  영향은 분리하지 않았다. "커널 문제"는 이 부팅 항목 전체를 가리킨다.
- 추론 스레드가 P-core와 E-core 중 어디에 놓였는지는 기록하지 못했다.
- 다음 시험: 같은 RT 부팅에서 `taskset -c 0-3` + `performance` governor로 재측정.
  21 FPS가 나오면 제어팀 설정을 바꾸지 않고도 해결된다.
